# ADR-0007: Prefixed UUIDv7 as Public IDs

**Date:** 2026-08-17
**Status:** Accepted

---

## Context

Every entity that crosses an API boundary (payments, merchants, API keys, refunds,
payouts) needs a stable public identifier. Three requirements drive the choice:

1. **Self-describing** — looking at a bare ID (`pay_…`, `mch_…`) should tell you
   what kind of entity it is, without a database lookup or documentation.
2. **Time-sortable** — ledger entries and transaction records are queried in
   chronological ranges. An ID that encodes creation time lets Postgres use the
   primary-key index for range scans instead of a separate `inserted_at` index.
3. **Safe to expose** — no sequential integers (enumerable), no timestamp-only
   IDs (guessable).

---

## Decision

All public entity IDs use **prefixed UUIDv7**, generated by the `uniq` library
(`uniq ~> 0.6.3`).

**Wire format** (API responses, logs, webhooks):
```
pay_018e4a1b-b0d4-7000-b9c2-f9c8e8d2ae4a
mch_018e4a1b-b0d5-7001-a1d3-e7f2c9b3df12
key_018e4a1b-b0d6-7002-b8e4-d1a0f6c2ab34
```

**Storage format** (Postgres): the full prefixed string is stored as a `TEXT`
column (`public_id TEXT UNIQUE NOT NULL`). The prefix is retained in the
database — it is not stripped on write or reconstructed on read.

**Prefix table** (maintained in context modules; each module's changeset
generates its own `public_id`):

| Prefix | Entity |
|--------|--------|
| `pay_` | Payment |
| `mch_` | Merchant |
| `key_` | API Key |
| `ref_` | Refund |
| `pyt_` | Payout |
| `sub_` | Subscription |
| `cus_` | Customer |
| `led_` | Ledger Entry |
| `stl_` | Settlement |
| `rcn_` | Reconciliation |

---

## Why UUIDv7 over ULID

| Property | ULID | UUIDv7 |
|----------|------|--------|
| Format | 26-char base32 | 36-char hex with dashes |
| Time-sortable | Yes | Yes |
| IETF standard | No (community spec) | Yes (RFC 9562, 2024) |
| Ecto support | Manual Ecto.Type required | Built into `uniq` |
| Collision safety | Yes | Yes |

The deciding factor is the IETF standard and native Ecto support. The internal
primary key `id` column uses the native Postgres `uuid` type (16 bytes), giving
B-tree index efficiency for FK relationships. The `public_id` column uses TEXT
and stores the full prefixed string — this is a deliberate trade-off explained
in the consequences below.

---

## Why TEXT storage for public_id

An earlier version of this ADR specified storing the raw UUID (16 bytes) in a
`uuid` column and reconstructing the prefix at the application layer. Phase 1
implementation revealed this adds complexity without meaningful benefit at
merchant/key table scale:

- Direct SQL queries work without transformation: `WHERE public_id = 'mch_018e…'`
- The database is self-documenting — a DBA can read a row and know the entity type
- Changeset code is simpler — `put_change(cs, :public_id, "mch_" <> Uniq.UUID.uuid7())`
- No risk of prefix/type mismatch in reconstruction logic

For very high-volume tables (ledger_postings, payment_events) where tens of
millions of rows accumulate, revisiting native `uuid` storage could save ~20
bytes per row. This ADR will be superseded if that trade-off changes.

---

## Consequences

**Positive**
- Chronological range queries on `payments`, `ledger_entries`, and
  `ledger_postings` use the primary-key `id` index (native `uuid`).
- Prefix makes support and debugging fast — a bare ID from a log or Slack alert
  identifies its own entity type without a lookup.
- Standard format: UUIDv7 is an IETF RFC; every tool understands it.
- TEXT `public_id` column is queryable directly; no application-layer
  transformation needed.

**Negative / Trade-offs**
- Public IDs are longer than ULID (40 chars with prefix vs 30 chars). Acceptable
  — Stripe's IDs are similar length.
- `public_id TEXT` adds ~36–40 bytes per row vs 16 bytes for native `uuid`.
  Negligible for entity tables (merchants, keys); may be revisited for
  append-only event tables at scale.
- UUIDv7 millisecond monotonicity means IDs generated in the same millisecond
  are ordered by random bits, not insertion order. Correct behaviour, not a bug.

**Implementation**
Generate with `Uniq.UUID.uuid7()`. Each schema module's `changeset/2` calls a
private `put_public_id/1` helper that generates and sets the prefixed ID on
insert only:

```elixir
defp put_public_id(%{data: %{public_id: nil}} = cs),
  do: put_change(cs, :public_id, "mch_" <> Uniq.UUID.uuid7())
defp put_public_id(cs), do: cs
```

URL-facing path params always carry the `public_id`. Context functions use
`Repo.get_by(Entity, public_id: id)` to resolve them. The internal UUID `id`
is never exposed in API responses or URL paths.
