# ADR 0003 — Prefixed UUIDv7 as Public IDs

Date: 2026-08-17
Status: Accepted

---

## Context

Every entity that crosses an API boundary (payments, merchants, transactions, refunds, payouts) needs a stable public identifier. Three requirements drive the choice:

1. **Self-describing** — looking at a bare ID (`pay_…`, `txn_…`) should tell you what kind of entity it is, without a database lookup or documentation.
2. **Time-sortable** — ledger entries and transaction records are queried in chronological ranges. An ID that encodes creation time lets Postgres use the primary-key index for range scans instead of a separate `inserted_at` index.
3. **Safe to expose** — no sequential integers (enumerate-able), no timestamp-only IDs (guessable).

The build bible listed "Prefixed ULIDs / UUIDv7" as alternatives; this ADR records the decision between them.

---

## Decision

All public entity IDs use **prefixed UUIDv7**, generated by the `uniq` library (`uniq ~> 0.6.3`).

**Wire format** (API responses, logs, webhooks):
```
pay_018e4a1b-b0d4-7000-b9c2-f9c8e8d2ae4a
txn_018e4a1b-b0d5-7001-a1d3-e7f2c9b3df12
mer_018e4a1b-b0d6-7002-b8e4-d1a0f6c2ab34
ref_018e4a1b-b0d7-7003-c9f5-a2b1d7e4cf45
```

**Storage format** (Postgres): native `uuid` column type (16 bytes). The prefix is an application-layer concern — it is added when serialising and stripped when deserialising. The database column stores only the raw UUID.

**Prefix table** (to be maintained in `Yagye.PublicId`):

| Prefix | Entity |
|--------|--------|
| `pay_` | Payment |
| `txn_` | Transaction |
| `mer_` | Merchant |
| `ref_` | Refund |
| `pyt_` | Payout |
| `sub_` | Subscription |
| `cus_` | Customer |

---

## Why UUIDv7 over ULID

| Property | ULID | UUIDv7 |
|----------|------|--------|
| Format | 26-char base32 | 36-char hex with dashes |
| Time-sortable | Yes | Yes |
| Postgres native type | No — stored as `text` or `bytea` | Yes — `uuid` (16 bytes, B-tree native) |
| IETF standard | No (community spec) | Yes (RFC 9562, 2024) |
| Ecto support | Manual Ecto.Type required | Built into `uniq` |
| Collision safety | Yes | Yes |

The deciding factor is the native Postgres `uuid` type. Storing as `uuid` means:
- 16 bytes vs 26 bytes per row (matters at ledger scale — hundreds of millions of rows)
- Primary-key and foreign-key indexes use the built-in UUID comparator, which is already time-ordered for v7
- No custom Ecto type needed; `uniq` ships `Uniq.UUID` as a drop-in for `Ecto.UUID`

---

## Consequences

**Positive**
- Chronological range queries on `payments`, `ledger_entries`, and `ledger_postings` use the primary key index with no extra `inserted_at` index.
- Prefix makes support and debugging fast — a bare ID from a log or Slack alert identifies its own entity type.
- Standard format: every database client, ORM, and monitoring tool understands `uuid` natively.

**Negative / trade-offs**
- Public IDs are longer than ULID (40 chars with prefix vs 30 chars). Acceptable — Stripe's IDs are similar length.
- The prefix lives only in the application layer, so internal tooling that queries Postgres directly won't see it. Convention: always use the API or context layer; never query `id` columns raw in ad-hoc scripts.
- UUIDv7 millisecond monotonicity means IDs generated in the same millisecond are ordered by random bits, not insertion order. This is correct behaviour and not a bug.

**Implementation note**
Generate with `Uniq.UUID.uuid7()`. The `Uniq.UUID` Ecto type handles `cast/load/dump` automatically. The serialisation layer (`Jason` encoder or a `Yagye.PublicId` module) adds and strips the prefix.
