# Provider Failure and Resolution Flow

Last updated: 2026-10-18

```
PROVIDER FAILURE AND RESOLUTION FLOW
======================================
Last updated: 2026-10-18

THE SCENARIO: MTN MOMO GOES DOWN
─────────────────────────────────

MTN MoMo is the dominant mobile money rail in Ghana. It experiences periodic
degradation: maintenance windows (2AM–4AM), high load at peak hours (lunch,
close of business), and occasional system incidents. This is the most
consequential failure mode for Yagye as a West African PSP.

──────────────────────────────────────────────────────────────────────────────

THE FULL RESOLUTION STATE MACHINE:

Customer makes GHS 200 payment
    │
    ▼
PaymentDispatchWorker:
  POST http://mtn-momo.ghana/v1_0/requesttopay
  X-Reference-Id: tok_018e...  ← OUR idempotency token sent TO MTN
  Body: { amount: "200", payer: { partyId: "024100..." } }
    │
    ▼  MTN accepts (HTTP 202) — USSD prompt sent to customer
    │
    │  Customer sees USSD: "Approve GHS 200 payment to Kofi's Shop"
    │  Customer approves...
    │
    ▼  [30 seconds pass — no callback from MTN]
    │
    ▼  Req.post timeout ({:error, :timeout})

     error_class = 'indeterminate'
     payment_attempt.state = 'resolution_pending'
     payment.state = 'processing'
     Oban: schedule ReconciliationWorker in +15 minutes
     LOG: {payment_id, idempotency_token: "tok_018e...", reason: "provider_timeout"}

──────────────────────────────────────────────────────────────────────────────

RECONCILIATION LOOP:

┌─────────────────────────────────────────────────────────────────────────────┐
│  ReconciliationWorker — Attempt 1 (T+15 min)                                │
│                                                                             │
│  GET /v1_0/requesttopay/tok_018e...                                         │
│  (query MTN for the outcome of OUR idempotency token)                       │
└──────────────────────────────────────────────┬──────────────────────────────┘
                                               │
                ┌──────────────────────────────┼─────────────────────────────┐
                │                              │                             │
                ▼                              ▼                             ▼
        MTN: SUCCESSFUL               MTN: FAILED            MTN: 503 / timeout
        (charge applied)              (not applied)          (MTN still down)
                │                              │                             │
                ▼                              ▼                             ▼
  Ecto.Multi:               UPDATE payment_attempts     Oban: reschedule
  UPDATE payment_attempts     state = 'timed_out'       delay: +30 min
    state = 'succeeded'     UPDATE payments               then: +2 hours
  UPDATE payments              state = 'failed'            then: +8 hours
    state = 'succeeded'     Outbox: payment.failed          then: +24 hours
  INSERT ledger_entries     event → portal, webhook         (max 7 days)
    (effective_at =
     ORIGINAL dispatch time,
     not now)
  INSERT ledger_postings
  Outbox: payment.succeeded
    event → portal + webhook

                │
                ▼
  Merchant receives payment.succeeded webhook
  (possibly 15 minutes after the customer paid —
   this is acceptable and documented behaviour)

──────────────────────────────────────────────────────────────────────────────

THE IDEMPOTENCY TOKEN — WHY IT'S CRITICAL:

  payment_attempts.idempotency_token = "tok_018e..."

  This is Yagye's token, sent to the provider as their idempotency key.
  Provider name for it:
    MTN MoMo:   X-Reference-Id header
    Stripe:     Idempotency-Key header
    Flutterwave: tx_ref body field

  WITHOUT the token: impossible to query MTN for a specific charge
    (amount + MSISDN is not unique — same customer, same amount, same day)

  WITH the token: GET /v1_0/requesttopay/{token} → definitive outcome

  The token is generated by Core before the HTTP request and stored
  immutably on the payment_attempt row.

──────────────────────────────────────────────────────────────────────────────

WORST CASE: 7-DAY WINDOW EXCEEDED

  ReconciliationWorker runs 7 consecutive days.
  Each attempt: MTN is unresponsive or returns inconsistent results.
  After 7 days:

    payment_attempt.state = 'abandoned'
    payment.state = 'abandoned'
    ops alert: HIGH SEVERITY — "Payment mch_018e.../pay_018e... requires manual review"

  Ops team:
    1. Contact MTN directly with the idempotency_token
    2. MTN confirms: charge applied OR not applied
    3. Manual ledger entry (via adjustment_approvals) if charge was applied
    4. Or: payment marked failed (safe to tell merchant)

  The abandoned state is the safety valve. It is never silently ignored.

──────────────────────────────────────────────────────────────────────────────

CIRCUIT BREAKER — PROTECTING FUTURE PAYMENTS:

  While the reconciliation loop is running for this payment,
  new payments are being dispatched.

  ProviderHealthTracker monitors per-provider failure rates:

  consecutive_indeterminate >= 5 in 15 minutes
    → circuit_breaker_state = 'open' for mtn_momo_gh
    → routing engine: no valid rule for MTN MSISDNs
    → new MTN payments fail fast: 'provider_circuit_open'
    → NOTE: NO fallback to Vodafone — MoMo rails don't allow cross-network
    → ops alert: "MTN MoMo GH circuit opened"

  After 5 minutes: circuit = 'half-open'
    → probe ONE payment through mtn_momo_gh
    → success: circuit = 'closed'
    → failure: circuit = 'open' (extended 10-minute wait)

  ML health predictor also learns:
    recent_success_rate_1h for mtn_momo_gh drops toward 0
    Model score → ops-visible degradation signal
    Used for: timing optimisation and aggregator selection (if multiple
    gateway paths exist for MTN), NOT for cross-network provider switching
    (circuit breaker = hard protection; ML score = soft health signal)

──────────────────────────────────────────────────────────────────────────────

OBAN WORKER RETRY BEHAVIOUR:

  PaymentDispatchWorker (on timeout):
    error_class = 'retryable_error' → Oban retry (new attempt on SAME payment)
    error_class = 'indeterminate'   → DO NOT retry dispatch
                                       enter reconciliation path instead

  This is critical. Retrying a dispatch on an indeterminate error
  would create a SECOND charge request to the provider:
    Attempt 1: timed out (charge may or may not have been applied)
    Attempt 2 (retry): new charge request → DOUBLE CHARGE if attempt 1 succeeded

  Indeterminate errors MUST go to ReconciliationWorker, NOT Oban dispatch retry.

──────────────────────────────────────────────────────────────────────────────

MERCHANT AND CUSTOMER EXPERIENCE:

  During resolution_pending:
    Merchant API: GET /v1/payments/{id} → state: "processing"
    Portal:       Payment shown as "Processing" (amber badge)
    Customer:     Nothing visible yet (Yagye waits for confirmation)

  After resolution (success, 15 min later):
    Merchant API: GET /v1/payments/{id} → state: "succeeded"
    Merchant webhook: payment.succeeded event delivered (with delay noted)
    Portal:       Payment shown as "Succeeded" (green badge, late timestamp)
    Customer:     Payment receipt sent (SMS at P18, if configured)

  After resolution (failed):
    Merchant API: GET /v1/payments/{id} → state: "failed"
    Merchant webhook: payment.failed event
    Portal:       Payment shown as "Failed" with reason: "provider_timeout_no_confirmation"
    Customer:     Safe to retry (no charge was applied)

──────────────────────────────────────────────────────────────────────────────

OBSERVABILITY:

  Grafana alert: count(payment_attempts WHERE state='resolution_pending'
                        AND payment_attempt.created_at < NOW() - 30min) > 10
  → "Provider timeout spike — check MTN MoMo health"

  Loki query:
    {app="yagye_core"} |= "resolution_pending" | json
    | line_format "{{.payment_id}} {{.provider_code}} {{.idempotency_token}}"

  Metric: yagye_payment_indeterminate_total (counter by provider_code)
  Metric: yagye_reconciliation_resolution_duration_seconds (histogram)
```
